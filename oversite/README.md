# `oversite` микросервис OverNode

`oversite` — сервис локального сайта. Он обслуживает файлы из заданного каталога
стандартным обработчиком Go `http.FileServer`. Адрес слушателя настраивается;
по умолчанию используется loopback.

## Конфигурация

| Параметр | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `httpd.listen_on` | `127.0.0.1:8000` | Адрес HTTP-слушателя. |
| `httpd.site_path` | нет | Обязательный каталог со статическими файлами. |
| `httpd.access_log_path` | нет | Необязательный журнал HTTP-запросов только в файл. |
| `logging.level` | `info` | Уровень журнала. |
| `logging.format` | `text` | Формат журнала: `text` или `json`. |
| `logging.file_path` | нет | Необязательный файл основного журнала; записи также выводятся в `stderr`. |

`httpd.site_path` задаётся аргументом, переменной окружения или файлом конфигурации;
пустое значение, отсутствующий путь и файл вместо каталога отклоняются. Относительный
путь разрешается от каталога файла конфигурации, а без него — от рабочего каталога.

Слушатель принимает любые числовые IP-адреса или пустой хост (`:8000`) для всех
интерфейсов. Имена вроде `localhost` не поддерживаются. Порт
должен быть числом от `0` до `65535`; `0` позволяет выбрать порт операционной системе.

При непустом `httpd.access_log_path` `httpd` создаёт отдельный access logger. Он
записывает в указанный файл метод, путь без query string, статус, размер ответа и
длительность каждого запроса; в `stderr` и основной журнал эти записи не попадают.
Пустой или незаданный путь отключает access log. Access log использует структурированный
текстовый формат; каталог для обоих файлов журналов должен существовать заранее.

Пример запуска:

```sh
go run ./oversite/cmd/oversite \
  --httpd.listen_on=127.0.0.1:8000 \
  --httpd.site_path=.local/var/www/html
```

Или через окружение:

```sh
HTTPD__SITE_PATH=.local/var/www/html go run ./oversite/cmd/oversite
```

## Локальный запуск

Из корня проекта:

```sh
go run ./oversite/cmd/oversite --httpd.site_path=.local/var/www/html
```

Или после сборки:

```sh
make build
.local/bin/oversite --httpd.site_path=.local/var/www/html
```

## Контейнерный образ

Образ собирается из корня репозитория командой:

```sh
docker build -f oversite/Dockerfile .
```

Dockerfile использует `common` и `oversite`, создавая для них временный `go.work` непосредственно внутри build-stage. Исходники `overgate` в этот образ не попадают.

В итоговом образе используется непривилегированный пользователь `65532:65532`.
Для Compose передайте путь к каталогу статического сайта на хосте: он монтируется в
контейнер только для чтения как `/site`.

```sh
OVERSITE_SITE_PATH="$PWD/.local/var/www/html" make up
```

Файлы и каталоги должны быть доступны для чтения непривилегированному пользователю
контейнера с UID/GID `65532`.

Вариант с постоянным локальным `compose.override.yaml` описан в
[корневом README](../README.md#быстрый-старт).

В Compose оба сервиса подключены к внутренней сети `backend`.
Сайт слушает `:8000`; overgate обращается к нему по адресу `http://oversite:8000`.
Порт 8000 на хост не публикуется.

## Проверка через Compose

Локальный `compose.override.yaml` публикует только порт прокси 2080;
пример приведён в [корневом README](../README.md).
После `make up` запросите сайт через прокси:

```sh
curl --noproxy '' -x http://127.0.0.1:2080 http://local.overspace/
```

Для прямого доступа к сайту на loopback хоста запускайте oversite локально,
как описано выше.
